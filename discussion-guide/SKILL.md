# discussion-guide

Turns research objectives into a moderated interview / usability-test guide. Inherits
`research-mode` — see that skill for the Automate / Assist / Protect (AAP) guardrails this one
runs under.

## What it produces

- An intro/consent script
- A question flow ordered from easy/warm-up to sensitive/core
- Suggested probes under each core question
- Task scenarios (if usability test) with success criteria
- A closing section (anything-else, thanks, incentive logistics)

This is a **guide**, not a script. It structures what to ask — it does not and cannot predict what
to probe on live, because that depends on what the participant actually says.

## AAP in this skill

- **Automate** — intro/consent boilerplate, section structure, closing logistics. Just produce it.
- **Assist** — question generation and probe suggestions from the plan's objectives. Offer
  multiple probe angles per question since the moderator won't know which one lands until they're
  in the room.
- **Protect** — **name explicitly that live probing is the moderator's call, not the guide's.**
  A guide that reads like a script invites a moderator to follow it rigidly instead of listening.
  Don't write it as a thing to be read verbatim.

## Workflow

1. Take objectives from `research-plan` (or ask for them directly if none exists).
2. Order questions: rapport-building → context → core topic → sensitive/hard questions →
   wrap-up. Easy stuff first, so the participant is warmed up before anything probing.
3. Under each core question, draft 2-3 possible probe directions — not a script, options.
4. If it's a usability test: draft task scenarios phrased as goals, not instructions ("you want to
   return an item you bought last week" not "click returns, then click item 3").
5. Add a line at the top of the guide: *"This is a guide, not a script — follow what the
   participant gives you, not just this order."*

## Common mistakes

- Writing probes as a fixed script ("if they say X, ask Y") — this is Assist material (a draft),
  not instructions to execute mechanically. The moderator reads the room, not the guide.
- Front-loading the most sensitive question before rapport is built.
- Task scenarios written as click-by-click instructions, which tests whether someone can follow
  directions rather than whether they can accomplish a goal.
